1. ОБЩАЯ СТРУКТУРА ОБЪЕДИНЕННОГО ПРОЕКТА
================================================================================
Все четыре лабораторные работы (№16, №17, №18, №19) объединены в единое
рабочее приложение NestJS в папке `nestjs-labs-16-19/`:

- ЛР №16 («NestJS и работа с базой данных»):
  * Подключение PostgreSQL через TypeOrmModule.forRootAsync() (src/app.module.ts).
  * Сущность Task (src/tasks/entities/task.entity.ts): id, title, description, completed.
  * Сущность User (src/users/entities/user.entity.ts): id, username, email, password.
  * Связь «один-ко-многим» (OneToMany / ManyToOne) между User и Task.
  * Полный CRUD для задач + получение всех задач конкретного пользователя
    (GET /tasks/user/:userId) и получение задачи по ID вместе со связанным
    пользователем (GET /tasks/:id).

- ЛР №17 («Аутентификация и авторизация в NestJS»):
  * Модуль AuthModule (src/auth/): регистрация POST /auth/register с хешированием
    пароля через bcrypt, вход POST /auth/login через Passport LocalStrategy.
  * Генерация и проверка JWT-токенов через JwtService и JwtStrategy.
  * Защита маршрутов задач и пользователей декоратором @UseGuards(JwtAuthGuard).
  * Ролевая модель доступа (RBAC): сущность Role (src/roles/entities/role.entity.ts)
    со стандартными ролями 'user' и 'administrator', связь «многие-ко-многим»
    (ManyToMany) между User и Role, кастомный декоратор @Roles() (@SetMetadata)
    и кастомный гард RolesGuard (защищает DELETE /tasks/:id и PATCH /users/:id/roles).

- ЛР №18 («Настройка окружения и деплой приложения в Docker»):
  * Dockerfile.basic — базовый одноступенчатый Dockerfile (Задание 1).
  * Dockerfile — оптимизированный многоступенчатый (multi-stage) Dockerfile
    с этапами builder и production на базе node:20-alpine (Задание 2).
  * docker-compose.yml — запуск двух связанных контейнеров: NestJS-приложения
    (app) и базы данных PostgreSQL (postgres) с общими переменными из .env.

- ЛР №19 («Развертывание приложения в облаке и настройка CI/CD»):
  * Динамический порт process.env.PORT || 3000 в src/main.ts и поддержка
    строки подключения DATABASE_URL в src/app.module.ts.
  * render.yaml — конфигурация Render Blueprint (вместо Heroku) для
    автоматического развертывания Docker-сервиса и базы данных PostgreSQL.
  * Эндпоинт GET /health (src/health/health.controller.ts) для проверки здоровья.
  * Юнит-тесты Jest (src/tasks/tasks.service.spec.ts, src/auth/auth.service.spec.ts).
  * .github/workflows/deploy.yml — CI/CD пайплайн GitHub Actions:
    checkout -> setup-node -> npm install -> npm test -> npm run build ->
    сборка и push Docker-образа в Docker Hub -> деплой на Render через Deploy Hook.

2. ЗАПУСК ПРОЕКТА ЛОКАЛЬНО В DOCKER (ЛР №18)
================================================================================
Требования: установленный Docker Desktop (или Docker Engine + Docker Compose).

Шаг 1. Распакуйте архив и откройте терминал в папке `nestjs-labs-16-19`:
    cd nestjs-labs-16-19

Шаг 2. Запустите сборку и старт контейнеров (приложение + PostgreSQL):
    docker compose up --build

(Если у вас старая версия Docker, используйте: docker-compose up --build)

Шаг 3. Дождитесь сообщений в логах:
    - postgres: database system is ready to accept connections
    - app: Application is running on: http://0.0.0.0:3000

Приложение готово к работе на http://localhost:3000 !
Таблицы в PostgreSQL (users, tasks, roles, user_roles) и базовые роли
('user', 'administrator') создаются автоматически при запуске.

[ДОПОЛНИТЕЛЬНО ДЛЯ ОТЧЕТА ПО ЛР №18, ЗАДАНИЕ 2 — СРАВНЕНИЕ РАЗМЕРОВ ОБРАЗОВ]:
Чтобы продемонстрировать преподавателю разницу между базовым и оптимизированным
многоступенчатым образами, выполните в терминале две команды сборки:
    docker build -f Dockerfile.basic -t nestjs-labs:basic .
    docker build -f Dockerfile -t nestjs-labs:optimized .
    docker images | grep nestjs-labs

Вы увидите, что базовый образ (`basic`) весит ~1.1 ГБ, а оптимизированный
многоступенчатый образ (`optimized`) на Alpine Linux — около ~180–200 МБ.

Для остановки контейнеров нажмите Ctrl+C или выполните:
    docker compose down

3. ТЕСТИРОВАНИЕ ВСЕХ ЗАПРОСОВ ЧЕРЕЗ POSTMAN (ЛР №16 и ЛР №17)
================================================================================
В архиве находится готовая коллекция `postman_collection.json`.

Шаг 1. Откройте Postman -> нажмите кнопку "Import" (слева вверху) -> выберите
файл `postman_collection.json`.

Шаг 2. В коллекции уже настроена переменная `{{baseUrl}} = http://localhost:3000`.
Кроме того, в запросы регистрации, входа и создания задачи встроены скрипты,
которые АВТОМАТИЧЕСКИ сохраняют полученный JWT-токен в переменную `{{token}}`,
ID пользователя в `{{userId}}` и ID задачи в `{{taskId}}`!

Шаг 3. Рекомендуемый порядок отправки запросов для демонстрации всех ЛР:
1) [0. Health Check] -> "Проверка работоспособности сервера (GET /health)"
   Ожидаемый ответ: 200 OK, {"status": "ok", ...}.

2) [1. Аутентификация] -> "1.1 Регистрация обычного пользователя (role: user)"
   Создает пользователя `student1` (пароль хешируется через bcrypt) и сохраняет
   его JWT-токен в `{{token}}` и ID в `{{userId}}`.

3) [2. Задачи CRUD] -> "2.1 Создать задачу для пользователя (POST /tasks)"
   Создает задачу в PostgreSQL, привязанную к `{{userId}}`. Сохраняет `{{taskId}}`.

4) [2. Задачи CRUD] -> "2.2 Получить все задачи (GET /tasks)"
   Показывает список задач (работает только при передаче заголовка
   Authorization: Bearer {{token}}; без токена вернет 401 Unauthorized).

5) [2. Задачи CRUD] -> "2.3 Получить все задачи пользователя (GET /tasks/user/{{userId}})"
   Демонстрирует выборку задач конкретного пользователя (ЛР №16, Задание 2).

6) [2. Задачи CRUD] -> "2.4 Получить задачу по ID со связанным пользователем (GET /tasks/{{taskId}})"
   Возвращает задачу вместе с вложенным объектом `user` (без поля password).

7) [2. Задачи CRUD] -> "2.5 Обновить задачу (PATCH /tasks/{{taskId}})"
   Меняет статус задачи на `completed: true`.

8) Демонстрация ролевого доступа (RBAC, ЛР №17, Задание 3):
   - Пока активен токен обычного пользователя `student1` (роль `user`), отправьте
     запрос "2.6 Удалить задачу (DELETE /tasks/{{taskId}})".
     Сервер вернет ошибку: 403 Forbidden ("требуется роль [administrator]").
   - Теперь выполните "1.2 Регистрация администратора (role: administrator)"
     (или "1.4 Вход администратора"). Токен администратора перезапишет `{{token}}`.
   - Повторно отправьте "2.6 Удалить задачу (DELETE /tasks/{{taskId}})".
     Теперь сервер вернет: 200 OK, {"deleted": true, "id": ...} !

4. РАЗВЕРТЫВАНИЕ В ОБЛАКЕ RENDER И CI/CD GITHUB ACTIONS (ЛР №19)
================================================================================
Вместо Heroku (которая больше не имеет бесплатного тарифа) проект настроен для
облачной платформы Render (https://render.com) с использованием Docker и
автоматического пайплайна GitHub Actions (`.github/workflows/deploy.yml`).

Шаг 1. Загрузите папку `nestjs-labs-16-19` в ваш репозиторий на GitHub
(например, ветка `main`). Важно: файл `.env` добавлен в `.gitignore` и не
попадет в репозиторий в целях безопасности (требование ЛР №18 и №19).

Шаг 2. Создайте базу данных и веб-сервис на Render (https://dashboard.render.com):
  Вариант А (Автоматически через Blueprint — файл `render.yaml`):
  1) В панели Render нажмите "New +" -> "Blueprint".
  2) Подключите ваш GitHub-репозиторий. Render автоматически прочитает файл
     `render.yaml`, создаст бесплатную БД PostgreSQL (`nestjs-labs-db`) и
     Docker Web Service (`nestjs-labs-16-19`), сам сгенерирует `JWT_SECRET` и
     передаст `DATABASE_URL` и динамический `PORT`.

  Вариант Б (Вручную через Web Service):
  1) Создайте PostgreSQL базу: "New +" -> "PostgreSQL" (Free tier) ->
     скопируйте "Internal Database URL".
  2) Создайте веб-сервис: "New +" -> "Web Service" -> выберите ваш репозиторий.
  3) В поле Runtime выберите "Docker" (Dockerfile Path: `./Dockerfile`).
  4) В разделе Environment Variables добавьте переменные:
     - `NODE_ENV` = `production`
     - `DATABASE_URL` = <вставьте Internal Database URL вашей БД>
     - `DB_SYNCHRONIZE` = `true`
     - `DB_SSL` = `true`
     - `JWT_SECRET` = <любая случайная секретная строка>
     - `JWT_EXPIRES_IN` = `1d`
  5) Нажмите "Deploy Web Service". После деплоя Render выдаст публичный URL
     вида `https://nestjs-labs-16-19.onrender.com`.

Шаг 3. Настройка автоматического CI/CD в GitHub Actions (`.github/workflows/deploy.yml`):
  1) В настройках вашего сервиса на Render перейдите в "Settings" ->
     найдите раздел "Deploy Hook" и скопируйте URL вебхука.
  2) В репозитории на GitHub откройте:
     Settings -> Secrets and variables -> Actions -> "New repository secret"
     и добавьте 3 секрета:
     - `DOCKERHUB_USERNAME` — ваш логин на hub.docker.com
     - `DOCKERHUB_TOKEN` — Access Token из настроек Docker Hub
     - `RENDER_DEPLOY_HOOK_URL` — скопированный Deploy Hook URL из Render
  3) При каждом `git push` в ветку `main` GitHub Actions автоматически:
     - скачает код и установит зависимости (`npm install`);
     - запустит юнит-тесты (`npm test`) — если тесты упадут, деплой остановится;
     - соберет проект (`npm run build`);
     - соберет оптимизированный Docker-образ и отправит его в Docker Hub;
     - вызовет `RENDER_DEPLOY_HOOK_URL` и запустит обновление сервиса на Render.

Шаг 4. Проверка облачного приложения через Postman:
  В Postman откройте настройки коллекции `NestJS Labs 16-19` -> вкладка
  `Variables` -> замените значение `baseUrl` с `http://localhost:3000` на ваш
  URL от Render (`https://nestjs-labs-16-19.onrender.com`) и выполните запросы.

5. КРАТКИЕ ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ (ДЛЯ ЗАЩИТЫ ЛР №16–19)
================================================================================

--- ЛАБОРАТОРНАЯ РАБОТА №16 (ORM, TypeORM, Prisma, PostgreSQL) ---
1. Что такое ORM и каковы его основные преимущества?
   ORM (Object-Relational Mapping) — технология связывания объектно-ориентированных
   классов кода с таблицами реляционной БД. Преимущества: ускорение разработки
   (готовые CRUD-методы), строгая типизация на TypeScript, защита от SQL-инъекций
   за счет параметризованных запросов, независимость от конкретной СУБД и
   управление схемой через миграции.

2. Как NestJS интегрируется с ORM (TypeORM)?
   Устанавливаются `@nestjs/typeorm`, `typeorm`, драйвер БД (`pg`). В корневом
   `AppModule` подключается `TypeOrmModule.forRoot()` / `forRootAsync()`, в
   дочерних модулях сущности регистрируются через `TypeOrmModule.forFeature([Entity])`,
   а в сервисы внедряется репозиторий через `@InjectRepository(Entity)`.

3. Как определяются сущности и первичный ключ в TypeORM?
   Класс помечается декоратором `@Entity()`. Первичный автоинкрементный ключ
   задается декоратором `@PrimaryGeneratedColumn()`, обычные столбцы — `@Column()`,
   а связи между таблицами — `@OneToMany`, `@ManyToOne`, `@ManyToMany` и `@JoinColumn`.

4. Как реализуются базовые CRUD-операции в TypeORM Repository?
   Create: `repo.create(dto)` + `repo.save(entity)`;
   Read: `repo.find()` (все записи) и `repo.findOne({ where: { id } })` (одна);
   Update: изменение полей сущности + `repo.save(entity)` (или `repo.update()`);
   Delete: `repo.remove(entity)` (или `repo.delete(id)`).

5. Для чего нужны миграции и почему `synchronize: true` нельзя в продакшене?
   Миграции позволяют контролируемо и версионируемо менять структуру БД без потери
   данных. Опция `synchronize: true` при каждом запуске автоматически перестраивает
   таблицы под код и может удалить столбцы/таблицы с реальными данными пользователей.

--- ЛАБОРАТОРНАЯ РАБОТА №17 (Аутентификация, JWT, Passport, RBAC) ---
1. В чем разница между аутентификацией и авторизацией?
   Аутентификация — проверка подлинности пользователя («кто ты?» по логину/паролю
   или токену). Авторизация — проверка прав доступа уже аутентифицированного
   пользователя к конкретным ресурсам и действиям («что тебе разрешено?»).

2. Опишите структуру JWT и роль цифровой подписи.
   JWT состоит из трех частей, разделенных точками (`Header.Payload.Signature`):
   Header (алгоритм и тип токена), Payload (полезная нагрузка: sub/id, username,
   roles, exp), Signature (цифровая подпись, вычисленная с помощью секретного
   ключа сервера). Подпись гарантирует целостность токена — его нельзя подделать
   или изменить без знания секретного ключа.

3. Как взаимодействуют NestJS и Passport.js (стратегии и гарды)?
   Стратегии (`LocalStrategy`, `JwtStrategy`) инкапсулируют логику проверки
   учетных данных или токена и возвращают объект пользователя. Гарды (`AuthGuard`)
   перехватывают HTTP-запрос до контроллера, запускают нужную стратегию и
   прикрепляют проверенного пользователя к `request.user`.

4. В чем разница между хешированием и шифрованием?
   Шифрование — обратимый процесс (данные можно расшифровать ключом). Хеширование —
   одностороннее криптографическое преобразование без возможности восстановить
   исходный пароль. Для паролей используется только хеширование (bcrypt).

5. Что такое «соль» (salt) при хешировании паролей?
   Соль — случайная строка, добавляемая к паролю перед хешированием. Она делает
   хеши уникальными даже для одинаковых паролей и защищает от атак по заранее
   вычисленным «радужным таблицам» (rainbow tables).

6. Как реализуется ролевая модель доступа (RBAC) в NestJS?
   Создаются сущности `User` и `Role` со связью `@ManyToMany` (промежуточная
   таблица `user_roles`), кастомный декоратор `@Roles(...)` на базе `@SetMetadata()`
   и гард `RolesGuard` (реализующий `CanActivate`), который сверяет роли из
   `request.user.roles` с требуемыми ролями маршрута.

--- ЛАБОРАТОРНАЯ РАБОТА №18 (Docker и Docker Compose) ---
1. Преимущества Docker по сравнению с виртуальными машинами (ВМ)?
   Контейнеры не запускают отдельную гостевую ОС с собственным ядром, а используют
   ядро хостовой ОС в изолированном пространстве. Поэтому контейнеры занимают
   в разы меньше места, запускаются за секунды и потребляют минимум RAM/CPU.

2. Назначение инструкций Dockerfile: FROM, WORKDIR, COPY, RUN, CMD.
   - FROM: задает базовый родительский образ (например, `node:20-alpine`).
   - WORKDIR: устанавливает рабочую директорию внутри контейнера.
   - COPY: копирует файлы с хоста в файловую систему образа.
   - RUN: выполняет команды на этапе сборки образа (например, `npm install`).
   - CMD: задает команду запуска приложения при старте контейнера.

3. Зачем нужна многоступенчатая сборка (multi-stage build)?
   Она позволяет на первом этапе (`builder`) установить компиляторы и devDependencies
   и скомпилировать TypeScript в JavaScript (`dist`), а в финальный образ (`production`)
   скопировать только `dist` и production-зависимости. Это уменьшает размер образа в 5–6 раз.

4. Что такое Docker Compose и когда он используется?
   Инструмент для описания и запуска многоконтейнерных приложений в одном файле
   `docker-compose.yml` (например, связка NestJS-сервера и СУБД PostgreSQL с общей
   сетью, томами данных и порядком запуска `depends_on`).

5. Как обрабатываются переменные окружения и почему `.env` не добавляют в Git?
   В NestJS переменные читаются через `@nestjs/config` (`ConfigService`) или
   `process.env`. Файл `.env` содержит секреты (пароли БД, `JWT_SECRET`), поэтому
   его добавляют в `.gitignore`, чтобы исключить утечку конфиденциальных данных.

--- ЛАБОРАТОРНАЯ РАБОТА №19 (Облачный деплой и CI/CD) ---
1. Основные принципы и преимущества CI/CD?
   CI/CD автоматизирует сборку, тестирование и доставку кода при каждом изменении
   в репозитории. Это ускоряет выпуск обновлений, исключает человеческий фактор
   и позволяет находить ошибки интеграции на самом раннем этапе.

2. Разница между Continuous Integration, Continuous Delivery и Continuous Deployment?
   - Continuous Integration (CI): регулярное слияние кода с автосборкой и автотестами.
   - Continuous Delivery: код автоматически проходит CI и готов к релизу, но выкладка
     в продакшн подтверждается вручную.
   - Continuous Deployment: полная автоматизация — после успешных тестов приложение
     само разворачивается в продакшн без ручного вмешательства.

3. Роль GitHub Actions и ключевые компоненты workflow-файла?
   GitHub Actions выполняет автоматические пайплайны прямо в репозитории. Основные
   секции YAML-файла: `on` (триггеры событий, например `push` в `main`), `jobs`
   (задания и среда выполнения `runs-on: ubuntu-latest`), `steps` (шаги: `uses`
   для готовых экшенов и `run` для консольных команд).

4. Как подготовить NestJS-приложение к облачному деплою (Render)?
   Использовать динамический порт `process.env.PORT || 3000` и привязку к `'0.0.0.0'`,
   поддержку облачной строки подключения `DATABASE_URL` с SSL, скрипт сборки
   `npm run build` и запуска `npm run start:prod`, а также healthcheck-эндпоинт.

5. Зачем нужны секреты (Secrets) в CI/CD?
   Секреты (например, `DOCKERHUB_TOKEN`, `RENDER_DEPLOY_HOOK_URL`) хранятся в
   зашифрованном виде в настройках репозитория и подставляются только во время
   выполнения пайплайна, предотвращая попадание ключей доступа в исходный код и логи.
